## 1. Test Case Overview

### 1.1 Scope

> **Source:** `scope.list` (which requirements are in and out) and Plan §2 (which levels and test types these cases serve). Not restated here.

This catalog covers journeys J1 and J2, the Orchestrator, the three Must agents, the approval gate, the audit log, the JobDiva connector and mocks, and the negative governance tests. These are Must scope under `scope.list`. It also covers the NFRs that the Test Plan assigns to QA-run verification. It is a single-cycle catalog for the 2026-10-28 submission and is **not exhaustive** of the FRS. Each exclusion and each gap is named below, not dropped.

**Exclusions** (`scope.list`, out-of-scope entries):
- FR-IGS-001, FR-IGS-002, FR-FBK-001, FR-FBK-002, FR-DSH-001, FR-DSH-002, FR-NHP-001 and FR-NHP-002 were excluded as Could priority with short time (entry 1). They are built since version 1.5 and have cases (§21H and §21I). The QSOT `scope.list` still records the exclusion, so this scope change needs confirmation by the Product Owner and Development (Test Plan Open Item 8).
- Real systems, real orders and production access are excluded (entry 2). The only cases that touch them are refusal tests (QC-COMP-N-001, QC-ACT-N-002).
- FLSA, classification, compensation and legal decisions are excluded. Only the escalation is tested (entry 3, BR-001), in QC-REC-N-001.
- The Should agents (FR-ACC, FR-CHK, FR-DOC, FR-PAY, FR-KB) were in scope only if built. They are built since version 1.5 and have cases. The code keeps them behind `FEATURE_*` flags, off unless set, and each test turns on the flag it needs.

**Basis of this revision (version 1.1).** The first version was generated without the FRS, the Backlog and the NFR text, and it assumed that only `tests/test_smoke.py` and `tests/unit/test_case_states.py` existed. This revision corrects that:

- **Requirements.** All 50 Must FRs of the FRS and all 31 NFRs of the NFR Register are traced individually (§23). The FR-ACT group is split into FR-ACT-001 to FR-ACT-008.
- **Expected results.** New cases and the corrected cases cite the Backlog story and acceptance criterion (US-xxx AC-yyy) or the NFR's own acceptance criteria. Cases from version 1.0 that still cite the Plan keep [AC-PENDING]: the tester checks them against the story's acceptance criterion before execution, and the acceptance criterion wins.
- **Code state.** Each case names the tests in the repository that cover it. The repository is main at PR #26 (commit efe5b3e merged). The recorded evidence shows 187 passing tests and 94% line coverage (`code/tests/evidence/`). These tests were read, not re-run, for this revision.
- **Agents and the model.** Agents run on the deterministic `rules` model engine (SAD ADR-006). There is no fake Velocity binding.
- **Business scenarios (version 1.2).** The demo scenario and the twelve acceptance criteria agreed with the onboarding team (checkpoint §3 and §7) are mapped to cases in §23.5 and §23.6, and the product gaps those cases expose are listed in §23.7. The raw transcript of the session was not available, so the checkpoint, which consolidates it, is the source.
- **Built since version 1.3 (version 1.5).** The Access and Equipment, Candidate Follow-up and Onboarding Knowledge agents, the document check and payroll handoff, team review, HR's answer, the IGS handoff and leader feedback, the new-hire package, the status dashboard, the model-assisted engine, the Coworker MCP server, the tray, the chat assistant, blank-value handling and the owner picker are in the repository. Main is at PR #52. The suite collects 383 tests: 382 pass with the optional tray extra installed (without it the 2 tray icon tests fail) and 1 is an expected failure (DEF-001). DEF-002 was fixed by pull request 47. Line coverage is 93%. These runs are mine of 2026-10-27; the recorded evidence in `code/tests/evidence/` is older.

**Coverage result at a glance** (computed in §23.4):
- Of 50 Must FRs, 50 have a case by design (a positive and a negative or edge case, or every acceptance criterion of the story mapped), 0 are partially covered and 0 are not covered. How many of those cases already have a test is in the execution column of §23.1.
- Of 31 NFRs, 31 have at least one case and 0 have none.
- There are 164 test cases in total: 117 executable today, 28 partly executable and 19 pending.

### 1.2 Test Case Naming Convention

> **Source:** `testcase-conventions.list`. Not restated beyond the format below.

IDs follow `QC-[MODULE]-[TYPE]-[NNN]`, with NNN numbered per module and type. Modules are grouped by FRS feature code (ITK, ADQ, VAL, REC, OWN, PKG, GATE, ACT, CASE, AUD, STS, WEB, PRV) and by NFR category for NFR cases (PERF, SEC, AVAIL, USE, REL, MAINT, COMPAT, COMP). Cases for the features built after version 1.3 use ACC, CHK, DOC, PAY, KB, IGS, FBK, NHP and DSH (stories US-020 to US-031), MDL (the model engine), INT (connectors and the Coworker MCP server) and TRY (the tray). The STS cases sit in the WEB section (§13). The ACC, CHK and KB cases of version 1.2 are in §21B and the newer ones in §21D to §21K. Priority is High, Medium or Low, aligned with MoSCoW (Must = High, Should = Medium, Could = Low).

Backlog story priorities were not available (see [AC-PENDING]). Priority is therefore differentiated by requirement criticality. High is used for inviolable-rule cases, the J1 and J2 critical path and exit-criteria checks. Medium is used for secondary validations and NFR checks that do not gate the demo. Low is used for maintainability and reproducibility checks. A story-level MoSCoW check should confirm or adjust these before execution.

### 1.3 Test Case Template

| Field | Description |
|-------|-------------|
| Test Case ID | Unique identifier, in the `testcase-conventions.list` format |
| Title | Brief description of what is verified |
| Module | Feature or NFR-category group |
| Type | Positive / Negative / Edge-Boundary |
| Priority | High / Medium / Low |
| Covers | FR-XXX / NFR-XXX / BR-XXX / UC-XXX verified |
| Source of Expected Result | Where the expectation comes from |
| Design Technique | The technique from Plan §2.3 the case applies |
| Dependencies | Cases that must pass first |
| Code State | Executable today / Designed, pending code (a `testcase-conventions.list` field) |
| Preconditions | Required state before the test starts |
| Test Steps | Numbered steps, each with an expected result |
| Test Data | TD-XXX sets from §22 |
| Expected Result | The overall outcome |
| Actual Result / Status | Filled in during execution |

**Common precondition for every case unless stated otherwise:** the local environment is running (`environments.list`), `JOBDIVA_MODE=mock`, and the seed scenarios have been loaded by the DB reset script.
