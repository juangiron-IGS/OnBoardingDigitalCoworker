## 1. System Overview

### 1.1 Purpose
The Onboarding Digital Coworker is a digital teammate that supports INSPYR's new-hire onboarding. Onboarding teams currently spend time chasing missing or inconsistent data from recruiters, picking paperwork from tacit rules and rebuilding information by hand. The result is slow document onboarding (about 3 days), wrong or missing forms, missed overhead and bill-back, payroll returns and dependence on a few people's knowledge.

The system takes a new hire's start from the JobDiva start email or a chat conversation. It asks adaptive questions and checks that the data is complete and consistent, flagging the exact field that is missing or contradictory. It recommends the onboarding path, the paperwork (citing the business rule that applies) and the onboarding owner. It prepares an approval package, and a human approves, returns or rejects it. Only after approval does it carry out actions, and in this hackathon those actions run against simulated systems only.

### 1.2 Scope
**In scope:**
- Intake by email and chat with adaptive questions.
- Validation of the 7 recruiter-note fields and the consistency rules.
- Business rules for paperwork (contract type, FLSA, state, city, client), onboarding owner (client type and role) and welcome kit (contract type).
- Access, equipment, overhead and bill-back (Should Have).
- Approval package and human approval gate.
- Simulated JobDiva, IT, equipment, payroll and email actions.
- Follow-up with a synthetic candidate (Should Have).
- Knowledge base with human validation (Should Have).
- Handoff to IGS with accelerated timing (Could Have).

Items deferred past v1 (pilot, scale-up, Microsoft Teams as a channel) are recorded in the Strategic Intake (SI-001, §4) and are not specified here.

### 1.3 Definitions
| Term | Definition |
|------|------------|
| FLSA | Fair Labor Standards Act classification of the new hire. It comes from the field or from HR and is never decided by the system |
| Work arrangement | Where the new hire will work. Today it is asked in three places and gives contradictory values, so the system keeps a single confirmed answer |
| Overhead | A percentage added to equipment cost: 2% (INSPYR) or 5% (Apple Direct) |
| Bill-back | Charging a cost back to the client according to a per-client rule. Where no client rule exists it is shown as an exception |
| Package version | Each revision of an approval package. An approval applies only to the version that was approved |
| Approval ID | The identifier recorded when a human approves a package version. Every simulated action must carry one |
| Audit log | The record of every action the system takes, with the action, agent, case, date, and the data and rules used |
| Validated knowledge | Knowledge-base content that the Onboarding Team has confirmed. Anything else is never presented as confirmed |
| Package line label | The label on each data point of the package: **source** (taken from JobDiva, the email or the chat), **inferred** (derived by the system from other data), **recommended** (proposed by a business rule) or **exception** (no rule applies, or a conflict needs a human) |
| Package status | Ready (complete, no blocking issue), blocked (cannot proceed, e.g. an escalated conflict) or needs clarification (waiting for an answer) |
| Case state | The step a case is in. The states and their transitions are listed in §3.8 (FR-CASE-001) |

### 1.4 Platform, Channel and Agents
The Coworker runs on Velocity 2.0. To users it is one Coworker, reached through a local web app with five views: chat, simulated email inbox, approval, simulated alerts and status (§3.20). The web app is the only mandatory channel, because Velocity 2.0 has no chat interface of its own. Every enterprise system is simulated and exposed to the agents as a tool or MCP server.

Inside, the Onboarding Orchestrator owns each case and routes work to specialized agents that share one context. Each capability has an owner agent:

| Owner agent | Priority | Capabilities |
|-------------|----------|--------------|
| Onboarding Orchestrator | Must | CAP-006, CAP-007, CAP-009, CAP-010, CAP-018 |
| Intake and Validation | Must | CAP-001, CAP-002, CAP-003 |
| Policy and Case Setup | Must | CAP-004, CAP-005 |
| JobDiva and Workflow | Must | CAP-008, CAP-014 |
| Access and Equipment | Should | CAP-011 |
| Candidate Follow-up | Should | CAP-012, CAP-013 |
| Onboarding Knowledge | Should | CAP-015 |
| Culture and Belonging (IGS) | Could | CAP-016, CAP-017, CAP-019 |

Notifications (email and Teams) are a shared tool with templates per audience, not an agent. The demo shows at least three specialized agents (Intake and Validation, Policy and Case Setup, JobDiva and Workflow) collaborating on one case under the orchestrator.

### 3.1 Intake from the JobDiva start email or chat — Traced To: CAP-001

**Feature Description:** The Coworker takes a new hire's start from the JobDiva start email or from a chat conversation. Priority: Must Have.

| ID | Requirement | Priority | Traced To |
|----|-------------|----------|-----------|
| FR-ITK-001 | The system shall accept a new hire's start from the automatic JobDiva start email received in the onboarding mailbox. | Must Have | CAP-001 |
| FR-ITK-002 | The system shall accept a new hire's start submitted through a chat conversation. | Must Have | CAP-001 |
| FR-ITK-003 | The system shall tolerate variations in the format of recruiter emails and ask the sender to confirm any value it cannot read with certainty. | Must Have | CAP-001 |

#### Acceptance Criteria

**FR-ITK-001:**
- Given a JobDiva start email arrives in the onboarding mailbox, when the system processes it, then a case is created containing the start data found in the email.

**FR-ITK-002:**
- Given a recruiter describes a new hire's start in chat, when the recruiter finishes the first message, then the system creates a case from the information given and continues the conversation on the same case.

**FR-ITK-003:**
- Given a recruiter email does not follow a standard format, when a value is ambiguous, then the system asks the sender to confirm that value before recording it as confirmed.

### 3.3 Completeness and consistency check — Traced To: CAP-003

**Feature Description:** The Coworker checks the 7 recruiter-note fields and the mandatory data for completeness and consistency, and alerts the recruiter with the exact field. Priority: Must Have.

- **The 7 recruiter-note fields:** work city and state (where the consultant works), FLSA, billing contact, timesheet approver, equipment (hardware tier and provider), sponsorship and visa, and additional notes (optional).
- **Mandatory JobDiva and chat data:** role, manager, start date, client, division, line of business, employment type and vendor company, work arrangement, and pay and bill rates.

| ID | Requirement | Priority | Traced To |
|----|-------------|----------|-----------|
| FR-VAL-001 | The system shall check that each of the 6 required recruiter-note fields is present in the case; additional notes is optional. | Must Have | CAP-003 |
| FR-VAL-002 | The system shall check that all mandatory JobDiva and chat data listed above is present. | Must Have | CAP-003 |
| FR-VAL-003 | The system shall apply the consistency rules and detect contradictory values for the same data point. | Must Have | CAP-003 |
| FR-VAL-004 | The system shall alert the recruiter, naming the exact field that is missing or contradictory. | Must Have | CAP-003 |
| FR-VAL-005 | The system shall not pass a case to the Onboarding Team with missing mandatory data unless the recruiter has been alerted about it. | Must Have | CAP-003 |

#### Acceptance Criteria

**FR-VAL-001:**
- Given a case whose JobDiva start notes are blank, when the check runs, then the 6 required recruiter-note fields are reported as missing by name, and additional notes is not reported.

**FR-VAL-002:**
- Given a case with one mandatory data point absent (for example the manager or the bill rate), when the check runs, then the case moves to Needs clarification and lists that data point.

**FR-VAL-003:**
- Given two sources give different values for the same data point, when the check runs, then the system flags a contradiction listing both values and their sources.

**FR-VAL-004:**
- Given a field is missing or contradictory, when the alert is sent, then the message names that exact field and not a generic "data incomplete" statement.

**FR-VAL-005:**
- Given a case has missing mandatory data, when it would be handed to the Onboarding Team, then an alert to the recruiter is already recorded in the audit log for each missing field.

### 3.6 Approval package — Traced To: CAP-006

**Feature Description:** The Coworker prepares an approval package where every data point carries a label and its source. Priority: Must Have.

| ID | Requirement | Priority | Traced To |
|----|-------------|----------|-----------|

| FR-PKG-003 | The system shall make the package ready for approval within 5 minutes of the last answer received. | Must Have | CAP-006 |

**FR-ACT-008:**

**FR-CASE-001:**

**FR-CASE-002:**

## 4. Use Cases

### UC-001: Start a case from a JobDiva start email or chat

| Field | Value |
|-------|-------|
| **ID** | UC-001 |
| **Actor** | Recruiter or hiring manager — UR-001 |
| **Goal** | Start a new hire's onboarding case with complete, consistent data |
| **Trigger** | The recruiter submits the start in JobDiva (automatic email) or opens a chat with the Coworker |
| **Preconditions** | No case exists for the same person and start date |
| **Postconditions** | A case exists with confirmed start data, ready for validation |

**Main Flow:**
1. The start email arrives in the onboarding mailbox or the recruiter writes in chat (FR-ITK-001, FR-ITK-002).
2. The system creates the case and asks the recruiter to confirm any ambiguous value (FR-ITK-003).
3. The system asks adaptive questions for what is missing, including a single work arrangement answer (FR-ADQ-001, FR-ADQ-002).
4. The system checks completeness and consistency (FR-VAL-001, FR-VAL-002, FR-VAL-003).

**Exceptions:**
- Duplicate person and start date: the system blocks the new case and names the existing one (FR-AUD-001, FR-AUD-003).
- Email format not recognized: the system asks the sender to confirm values (FR-ITK-003).
