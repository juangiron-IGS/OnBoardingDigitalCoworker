## 1. Introduction

### 1.1 Purpose

This document provides technical guidance for developers working on the Onboarding Digital Coworker. It covers environment setup, project structure, development patterns, testing, build and CI, and troubleshooting. It builds on the architecture and code-structure decisions already made in Phases 2 and 3 and does not re-decide any of them.

### 1.2 Audience

- Development team members (six people, see `ctx.list`)
- New team members being onboarded
- Reviewers who need to run the demo locally
- Technical support staff

### 1.3 Prerequisites

> **Source:** Phase 3 Answers record, `ctx.list` (Codebase Context). The codebase is **greenfield**. There is no prior release, so no existing conventions carry forward. The team has six members and builds against the October 28, 2026 submission.

- Familiarity with the established technology stack (Section 2.2)
- Access to the GitHub repository
- A development environment set up as described in Section 4
- A container runtime on your machine (required for the local PostgreSQL, SAD §2.4)

## 3. Technical Constraints — Implementation Guidelines

> **Source:** the constraints come from Phase 2's Answers record, `tc.list`, as reproduced in SAD §1.2. They are not restated here. This section only translates each binding constraint into concrete day-to-day guidance.

| Constraint (see SAD §1.2) | Concrete Implementation Guideline |
|---------------------------|-----------------------------------|
| TC-001 | Agents and the orchestrator are built on Velocity 2.0 and live under `agents/`. Do not add a second agent framework. Only the agent runtime depends on Velocity 2.0. The case service and MCP servers must not import it |
| TC-002 | Every server binds to `127.0.0.1`. Never use `0.0.0.0` in any config, compose file or start script. There is no hosted environment, so there is no deploy stage in CI (Section 8.2) |
| TC-003 | Seed scenarios under `db/seed/` are synthetic only. Never commit or load a real candidate record. Never add a JobDiva write call. `JOBDIVA_MODE` defaults to `mock` |
| TC-004 | Every model call goes through `agents/common/usage_meter.py`, which records usage per run and per case and refuses a call once `MODEL_USAGE_CAP_PER_RUN` is reached. Use smaller models for extraction steps |
| TC-005 | Teams is a mock MCP server (`mcp_servers/mocks/teams`) that writes into the simulated alerts view. Keep `TEAMS_MODE=mock`. The `bot` value and the `MS_*` and `TEAMS_BOT_*` variables in `code/.env.example` are reserved for the pilot. Never add a Teams bot, bot registration code or tenant dependency |

Constraints implied by Alternative B (SAD §1.2, second table). These are not formally declared TC items but are binding on this codebase:

| Implied constraint (SAD §1.2) | Concrete Implementation Guideline |
|-------------------------------|-----------------------------------|
| Write tools only in the JobDiva and Workflow server, which re-verifies approval ID and package version | Register `@mcp.tool()` write tools only under `mcp_servers/jobdiva_workflow/tools/`. A governance test (Section 7.4) fails if any other server registers a write tool |
| Audit table writable by INSERT only | Application code writes audit rows through the `audit_writer` database role only (Section 4.5). Never grant UPDATE or DELETE on the audit table |
| JobDiva token in memory only, confined to the READ server | Load the token in `mcp_servers/jobdiva_read/config.py`. Never place it in another process's environment, in a log line, or in the database |
| `JOBDIVA_MODE` fixed at startup, default `mock`, never switched at runtime | Read it once at process start and refuse to start on any value other than `mock` or `sandbox` |
| Mock stores in the same PostgreSQL instance as the audit table | Mock servers use the same database through their own schema, so an action and its audit entry commit in one transaction |
| Idempotency key built from approval ID and action | Always build it with the helper `contracts.mcp_tools.idempotency_key(approval_id, action)` |
| Shared case ID (correlation ID) in every process log | Use the shared logging setup in Section 6.3 |
| Container runtime on every demo machine | Document and check it in `scripts/start.sh` (Section 4.4) |
| All inter-process links bind to loopback only | Same rule as TC-002 |
| No write to JobDiva in any mode, including sandbox (ADR-004, BR-014) | No code path may call a JobDiva write endpoint. A write requested in sandbox mode is refused and audited |

> **Note:** Any deviation from a Technology Constraint requires written approval from the Solution Architect and must be logged as an ADR in the Software Architecture Document.

### 4.4 Local Services Setup

> **Source:** Phase 3's Answers record, `tool.list`, which names the local setup specifics: a README with install and run commands, a single-command start with health checks, a reset command that recreates the PostgreSQL volume and reloads the seed scenarios, and a backup demo video. Infrastructure shape from the SAD (§2.3, §2.4).

The local PostgreSQL runs in a container with a named volume. See Section 8.3 for `docker-compose.yml`.

```bash
./scripts/start.sh     # single-command start
./scripts/reset.sh     # recreate the PostgreSQL volume and reload the seed scenarios
```

On Windows, run these from Git Bash or WSL (Section 4.1).

`scripts/start.sh` does the following in order:

1. Checks that the container runtime is running and exits with a clear message if not.
2. Starts the PostgreSQL container and waits until it reports healthy.
3. Runs `scripts/apply_db.sh` when the volume is new, which applies migrations, roles and seed data (Section 4.5). On later starts the existing data is kept.
4. Starts the case service, the web app and API, the JobDiva READ and JobDiva and Workflow servers, the mock servers and the orchestrator, all on `127.0.0.1`.
5. Runs `scripts/health_check.py`, which calls each process's health endpoint and prints one line per process. The start fails if any health check does not pass.

`scripts/reset.sh` stops the processes, removes the PostgreSQL named volume, recreates it and runs `scripts/apply_db.sh` again. All data except cases, approvals and audit is synthetic and regenerable (ADR-002).

A backup demo video is kept as the offline fallback for presentation day (SAD §2.4).

### 4.5 Database Setup

Migrations are plain, ordered SQL files in `db/migrations/`. This avoids introducing an ORM or migration tool the sources do not establish. Tables are created only in migrations. Role scripts in `db/roles/` only create roles and grant privileges. Seed scenarios live in `db/seed/`. `scripts/apply_db.sh` applies the three folders in that order. `start.sh`, `reset.sh` and CI all call it.

```bash
# scripts/apply_db.sh (excerpt): migrations, then roles, then seed data
export PGPASSWORD="${DB_ADMIN_PASSWORD}"
PSQL=(psql -h 127.0.0.1 -p "${DB_PORT}" -U postgres -d "${DB_NAME}" -v ON_ERROR_STOP=1)

for f in db/migrations/*.sql; do "${PSQL[@]}" -f "$f"; done
for f in db/roles/*.sql; do
  "${PSQL[@]}" -v app_password="${DB_APP_PASSWORD}" -v audit_password="${DB_AUDIT_PASSWORD}" -f "$f"
done
for f in db/seed/*.sql; do "${PSQL[@]}" -f "$f"; done
```

The audit log records every agent action with its agent, case, data used and rules used (checkpoint data model and AC9). Restricted data is referenced by field, never by value:

```sql
-- db/migrations/001_audit_log.sql
CREATE TABLE IF NOT EXISTS audit_log (
    id              BIGSERIAL   PRIMARY KEY,
    case_id         TEXT        NOT NULL,
    agent           TEXT        NOT NULL,          -- orchestrator, intake_validation, jobdiva_workflow, ... or a human role
    action          TEXT        NOT NULL,
    outcome         TEXT        NOT NULL,          -- completed | refused | failed
    approval_id     TEXT,
    package_version INTEGER,
    rule_ids        TEXT[]      NOT NULL DEFAULT '{}',  -- rules used, for example {R-PA-02}
    data_refs       JSONB       NOT NULL DEFAULT '{}',  -- data used: field names and sources, never restricted values
    recorded_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The audit table is append-only by role (NFR-SEC-004, ADR-002):

```sql
-- db/roles/001_roles.sql
SELECT format('CREATE ROLE coworker_app LOGIN PASSWORD %L', :'app_password')
WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'coworker_app') \gexec
SELECT format('CREATE ROLE audit_writer LOGIN PASSWORD %L', :'audit_password')
WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'audit_writer') \gexec

REVOKE ALL ON audit_log FROM PUBLIC;
GRANT SELECT, INSERT ON audit_log TO coworker_app;   -- INSERT: action and audit in one transaction
GRANT INSERT ON audit_log TO audit_writer;           -- standalone writes
GRANT USAGE ON SEQUENCE audit_log_id_seq TO coworker_app, audit_writer;
-- No UPDATE, DELETE or TRUNCATE on audit_log is granted to any application role.
```

`coworker_app` needs INSERT on the audit table because a simulated action and its audit entry must commit in one transaction (NFR-REL-002), and a transaction cannot span two connections with different roles. The audit adapter therefore writes on the caller's connection. The table stays append-only, because no role can change or delete an entry. The full grants, including the case tables, are in `code/db/roles/001_roles.sql`.

The role passwords come from `.env` through `psql` variables when the script runs. They are never committed.

### 4.6 Running the Application

```bash
# normal run (all processes, mock mode)
./scripts/start.sh

# run one process on its own for development (Lane A example)
uvicorn web.api.main:app --host 127.0.0.1 --port 3000 --reload

# debug: verbose logging
LOG_LEVEL=DEBUG ./scripts/start.sh

# sandbox mode (read-only), only when sandbox credentials are in .env
JOBDIVA_MODE=sandbox ./scripts/start.sh
```

The web app is served at `http://127.0.0.1:3000` (`WEB_APP_PORT`). There is no separate production-mode run: the system runs on localhost only (TC-002), and the demo uses the same start command.

## 5. Project Structure

### 5.1 Directory Structure

> **Source:** Phase 3's Answers record, `struct.list` (Code Structure & Component Mapping) for the folder of each component, one entry per component. `repo.list` for the single-tree monorepo. `struct.list` records the layering pattern for **every** component as "Deferred — Technical Documentation to propose", so Case B applies to all of them. Each component's pattern is analyzed below against the established language and framework (Python and FastAPI, assumed default, STACK-006), the component's role in SAD §1 and §3, and the quality priorities in SAD §1.1: security first, then testability and replaceability of connectors.

#### Pattern analysis per component (Case B)

**STRUCT-001 — Web app (`web/ui`)**

| Candidate | Fit for a lightweight browser front-end served by FastAPI |
|-----------|-----------------------------------------------------------|
| Type-based folders (`html/`, `css/`, `js/`) | Simple, but the five views scatter across three folders |
| **View-per-folder (feature-based)** | Each of the five views owns its markup, script and styles. Fits the five views and the Lane B ownership |
| Component-framework layout (React or similar) | No front-end framework is established by STACK-003. Not considered viable without a new decision |

Recommended: **view-per-folder**, with a `shared/` folder for the API client and role selector. File names use kebab-case (`conv.list`).

**STRUCT-002 — API / web layer (`web/api`)**

| Candidate | Fit for FastAPI |
|-----------|-----------------|
| Controller / service / repository | The API holds no persistence, because the case service owns state. The repository layer would be empty |
| Hexagonal | Over-built for a layer that only serves views and forwards decisions |
| **Router-per-feature (FastAPI's conventional `routers/` layout) with thin handlers** | Idiomatic FastAPI. One router per view, handlers only validate input and call the case service interface |

Recommended: **router-per-feature**. Handlers contain no business logic, which keeps the approval gate in one place (the case service).

**STRUCT-003 — Case service (`services/case_service`)**

| Candidate | Fit |
|-----------|-----|
| N-layer (api, service, repository) | Familiar for FastAPI, but the approval gate would depend on the database layer, which makes the negative governance tests heavier |
| Vertical slicing | Good for independent features. The case service is one cohesive aggregate with a few shared invariants (approval, package version, audit) |
| **Hexagonal (ports and adapters)** | Keeps the approval gate and package-version rules as pure Python in `domain/`, testable without PostgreSQL. PostgreSQL and the rules files sit behind ports. The JobDiva and Workflow server can reuse the same pure gate. Fits the testability and security priorities |

Recommended: **hexagonal**, in the idiomatic Python form of `domain/`, `application/`, `ports/`, `adapters/`.

**STRUCT-004 — Orchestrator and agents (`agents/`)**

| Candidate | Fit |
|-----------|-----|
| Layered (all prompts, all tools, all schemas in shared folders) | Couples agents together and blocks parallel work |
| **Package-per-agent (feature-based)** with a `common/` package | One folder per agent: the orchestrator and the Must, Should and Could agents (checkpoint Section 5, STACK-002). Failure and ownership are isolated, which matches "a Should agent's failure does not stop J1 or J2" |
| Hexagonal per agent | Heavy for agents that mostly call MCP tools and models |

Recommended: **package-per-agent**. Each agent folder holds its code, its prompt (`prompt.md`) and its skills (`skills/`), which the submission package requires. The Velocity 2.0 binding is contained in `agents/common/`, so the rest of the code does not depend on it directly. The exact Velocity 2.0 SDK calls are confirmed in the day-one spike. Notifications (email and Teams) are a shared tool in `agents/common/notifications.py`, not an agent (checkpoint Section 5). Their templates per audience live in `rules/templates/`.

**STRUCT-005, 006, 007 — MCP servers (`mcp_servers/`)**

| Candidate | Fit |
|-----------|-----|
| One flat module per server | Fastest to write, but mock and sandbox modes and the approval re-check become tangled |
| **Shared server template: `server.py` (registration), `tools/`, `adapters/` (mock vs. sandbox), plus `guards/` where a server writes** | The template is what the architecture phase's mitigation relies on (one shared MCP server template). One MCP interface across mock, sandbox and real modes (NFR-COMPAT-002) |
| Hexagonal per server | The adapter split gives the same benefit without the extra layers |

Recommended: **the shared server template**, with a supporting `mcp_servers/common/` package.

**STRUCT-008 — Rules catalog and templates (`rules/`)**

Data only, so no code pattern applies. The folder is organized by rule domain (paperwork, kit, owners, notifications, templates), with each file carrying a rule ID.

**STRUCT-009 — Case store and audit log (`db/`)**

Data only. Ordered SQL migrations, role scripts and seed scenarios. PostgreSQL itself runs in a container.

#### Resulting tree

**Case service — domain (pure Python, no database)**

```python
# services/case_service/domain/errors.py
class GovernanceError(Exception):
    """Base class for refusals that are expected, audited outcomes."""

    def __init__(self, reason: str) -> None:
        super().__init__(reason)
        self.reason = reason


class ApprovalRefused(GovernanceError):
    """reason: "no_approval" | "version_mismatch" (BR-002)."""
```

```python
# services/case_service/domain/approval_gate.py
from dataclasses import dataclass

from .errors import ApprovalRefused


@dataclass(frozen=True)
class Approval:
    approval_id: str
    case_id: str
    package_version: int


def verify(approval: Approval | None, current_package_version: int) -> None:
    """Raise ApprovalRefused unless the approval matches the current package version (BR-002)."""
    if approval is None:
        raise ApprovalRefused("no_approval")
    if approval.package_version != current_package_version:
        raise ApprovalRefused("version_mismatch")
```

**Case service — case states (checkpoint Section 5, "Case states")**

The case states and their transitions live in the domain as data, so the case service refuses any transition that is not listed. A duplicate (same person and start date) blocks the case at Received. A returned package goes back to Validated. Any change creates a new package version and needs a new approval. A rejected case stays stopped.

```python
# services/case_service/domain/case.py (excerpt)
```

**Case service — ports and application**

```python
# services/case_service/ports/audit_log.py
from typing import Protocol


class AuditLog(Protocol):
    def append(self, *, case_id: str, agent: str, action: str, outcome: str,
               approval_id: str | None = None, package_version: int | None = None,
               rule_ids: list[str] | None = None,
               data_refs: dict[str, str] | None = None) -> None: ...
    # data_refs maps field names to their source. Restricted fields appear by name, never by value.
```

```python
# services/case_service/application/record_approval.py
from ..domain.approval_gate import Approval, verify
from ..domain.errors import ApprovalRefused
from ..ports.audit_log import AuditLog
from ..ports.case_repository import CaseRepository


def record_approval(repo: CaseRepository, audit: AuditLog, *, case_id: str,
                    package_version: int, approver_role: str) -> str:
    current = repo.current_package_version(case_id)
    try:
        verify(Approval("pending", case_id, package_version), current)
    except ApprovalRefused as refusal:
        audit.append(case_id=case_id, agent=approver_role, action="approve_package",
                     outcome="refused", package_version=package_version)
        raise
    with repo.transaction():                       # approval and audit commit together
        approval_id = repo.insert_approval(case_id, package_version, approver_role)
        audit.append(case_id=case_id, agent=approver_role, action="approve_package",
                     outcome="completed", approval_id=approval_id,
                     package_version=package_version)
    return approval_id
```

**API layer — a thin router (router-per-feature)**

```python
# web/api/routers/approvals.py
from fastapi import APIRouter, Depends, HTTPException

from contracts.case_service_api import CaseServiceClient
from services.case_service.domain.errors import ApprovalRefused
from ..deps import get_case_service

router = APIRouter(prefix="/approvals", tags=["approvals"])


@router.post("/{case_id}")
def approve(case_id: str, package_version: int, role: str,
            svc: CaseServiceClient = Depends(get_case_service)):
    try:
        return {"approval_id": svc.record_approval(case_id, package_version, role)}
    except ApprovalRefused as refusal:
```

### 6.2 Error Handling

> **Source:** `conv.list` and `sec.list` record no specific error-handling approach. The audit and refusal requirements come from the SAD (§2.2, §3.2).

- Governance refusals are **domain exceptions** (`ApprovalRefused`), never silent returns. A refusal is always written to the audit log before the error reaches the caller. This applies to a missing approval, a version mismatch, a duplicate, and a write requested in sandbox mode.
- A failed dependency (an MCP server or the model call) fails the step visibly. The case keeps its state, the package status becomes blocked, an alert is shown, and the failure is logged with the case ID (SAD §2.2).
- A failing Should agent adds an exception line to the package and never stops J1 or J2.
- Error messages and audit entries refer to restricted data (visa, sponsorship, FLSA) by field reference, never by value (`sec.list`).
- Retrying pending actions after a failure reuses the same approval ID and idempotency key, so completed actions are never duplicated (NFR-REL-005).

```python
# agents/common/mcp_client.py (excerpt)
class McpCallFailed(Exception):
    def __init__(self, server: str, tool: str, case_id: str):
        super().__init__(f"{server}.{tool} failed for case {case_id}")
```

### 6.3 Logging

> **Source:** `sec.list` — no credentials in any log, and restricted data logged by field reference, not by value.

All processes use one logging setup with a shared case ID (correlation ID) and a redaction filter:

```python
# mcp_servers/common/logging_setup.py
import json
import logging
import os
import re

_SECRET = re.compile(r"(password|token|authorization|api[_-]?key)\s*[=:]\s*\S+", re.IGNORECASE)


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        message = _SECRET.sub(r"\1=[redacted]", record.getMessage())
        return json.dumps({
            "ts": self.formatTime(record),
            "level": record.levelname,
            "process": os.environ.get("PROCESS_NAME", "unknown"),
            "case_id": getattr(record, "case_id", None),
            "message": message,
        })


def configure(process_name: str) -> None:
    os.environ["PROCESS_NAME"] = process_name
    handler = logging.StreamHandler()
    handler.setFormatter(JsonFormatter())
    logging.basicConfig(level=os.environ.get("LOG_LEVEL", "INFO"), handlers=[handler], force=True)
```

Pass the case ID with `logger.info("package ready", extra={"case_id": case_id})`. A governance test (Section 7.4) fails if a token appears in any captured log output.

### 6.4 Build Order and Parallel Lanes

> **Source:** Phase 3's Answers record, `extra.mvp-priority` (extracted) and `extra.parallel-lanes` (assumed default).

**MVP first.** Build the Must scope first: journeys J1 (intake and validation) and J2 (package, approval and simulated actions). That means the Must agents, the approval gate, the audit log, the JobDiva connectors and mocks they need, and the negative governance tests. Access and Equipment, Candidate Follow-up, Onboarding Knowledge, Culture and Belonging, and reminders are built only after the MVP works end to end.

**Two independent lanes.** Lanes work in separate folders and meet only at the interface contracts.

| Lane | Owns |
|------|------|
| **Lane A — governance core** | `services/case_service/`, `db/`, `mcp_servers/jobdiva_workflow/`, `web/api/`, `scripts/` |
| **Lane B — intelligence and connectors** | `agents/`, `velocity/`, `mcp_servers/jobdiva_read/`, `mcp_servers/mocks/`, `rules/`, `web/ui/` |

The submission items outside `code/` (`README.md`, `LICENSE`, `Documents/Submission/`) are shared and are closed out in the hardening phase (SAD §1.1, October 26–28).

The case service API and the MCP tool signatures are defined first in `contracts/` and stubbed, so neither lane waits on the other. Changing a contract needs a pull request approved by someone from each lane.

```python
    # Act / Assert: approving the old version is refused
    with pytest.raises(ApprovalRefused):
        record_approval(repo, audit, case_id=case_in_approval_gate, package_version=1, approver_role="approver")
```

## 8. Build and Deployment

### 8.1 Build Process

There is no compiled artifact. The build is installing dependencies and running the quality gates, from `code/`:

```bash
cd code
pip install -e ".[dev]"
ruff check .
ruff format --check .
pytest --cov=. --cov-fail-under=70
```

### 8.2 CI/CD Pipeline

> **Source:** Phase 3's Answers record, `tool.list` (GitHub Actions for the test workflow, assumed default; GitHub for the repository and pull requests) and `review.list` (a merge requires the workflow to pass). The system runs on localhost only (TC-002), so there is **no deployment or release stage**. CI is the test workflow only.

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: ci-only-password
          POSTGRES_DB: coworker
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    defaults:
      run:
        working-directory: code
    env:
      DB_PORT: "5432"
      DB_NAME: coworker
      DB_ADMIN_PASSWORD: ci-only-password
      DB_APP_PASSWORD: ci-only-app
      DB_AUDIT_PASSWORD: ci-only-audit
      DATABASE_URL: postgresql://coworker_app:ci-only-app@127.0.0.1:5432/coworker
      AUDIT_DATABASE_URL: postgresql://audit_writer:ci-only-audit@127.0.0.1:5432/coworker
      JOBDIVA_MODE: mock
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"        # keep aligned with pyproject.toml
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: ruff format --check .
      - name: Apply migrations, roles and seed data
        run: ./scripts/apply_db.sh
      - run: pytest --cov=. --cov-report=term-missing --cov-fail-under=70
```

The 70% coverage gate and the negative governance tests are enforced here (QUAL-006, QUAL-004). The CI database passwords are throwaway values used only on the CI runner. Real credentials are never stored in the workflow. The PostgreSQL image tag and Python version are working defaults, aligned with the assumed stack.

### 8.3 Container/Deployment Build

Only PostgreSQL runs in a container (ADR-002, SAD §2.3). Nothing else is containerized.

```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:16
    ports:
      - "127.0.0.1:${DB_PORT:-5432}:5432"      # loopback only (TC-002)
    environment:
      POSTGRES_DB: ${DB_NAME:-coworker}
      POSTGRES_PASSWORD: ${DB_ADMIN_PASSWORD}
    volumes:
      - coworker_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  coworker_pgdata:
```

`scripts/reset.sh` removes `coworker_pgdata` and reapplies migrations and seed data.

## 9. Troubleshooting

### 9.1 Common Issues

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `start.sh` stops with "container runtime not running" | The container runtime is not started | Start Docker or Podman and rerun |
| PostgreSQL never becomes healthy | Port already in use, or a corrupted volume | Change `DB_PORT` in `.env`, or run `./scripts/reset.sh` |
| A process refuses to start with `JOBDIVA_MODE must be one of ['mock', 'sandbox']` | Invalid value in `.env` | Set `JOBDIVA_MODE=mock` or `sandbox`. It cannot change while running |
| Sandbox mode returns no data | Sandbox credentials missing or wrong | Sandbox mode needs credentials in `.env`. Without them, use `mock` |
| A write to JobDiva is refused in sandbox mode | This is by design (ADR-004, BR-014) | Create test candidates by hand in the JobDiva sandbox web interface |
| Approval rejected with "version_mismatch" | The package changed after the approver opened it | Reload the approval view and approve the current version. Each change invalidates earlier approvals |
| Action refused by the workflow server | Missing approval ID or version re-verification failed | Check the audit log for the refusal reason, then re-approve the current version |
| `permission denied for table audit_log` on UPDATE or DELETE | Expected. The audit table is INSERT-only | Never update the audit table. Insert a new entry instead |
| Audit insert fails with permission denied | The wrong database role is configured | Make sure the audit writer connects with `AUDIT_DATABASE_URL` |
| `apply_db.sh` fails with "role already exists" or duplicate seed rows | The script ran against a volume that already has data | Run `./scripts/reset.sh`. `start.sh` applies the database only to a new volume |
| `./scripts/start.sh` does nothing or "bad interpreter" on Windows | Run from PowerShell or cmd | Run it from Git Bash or WSL |
| Model calls stop mid-run | `MODEL_USAGE_CAP_PER_RUN` reached (TC-004) | Raise the cap in `.env` only with the team's agreement, or start a new run |
| A Should agent failed, and the package has an exception line | By design. A Should agent failure does not stop J1 or J2 | Check that agent's logs for the case ID |
| Demo fails on presentation day | Many local processes (about nine) plus a container | Run `./scripts/reset.sh`, then `./scripts/start.sh`. If it still fails, use the backup demo video |
| `ruff` or `pytest --cov-fail-under` fails in CI | Style violation or coverage below 70% | Run `ruff format .` locally and add the missing tests |

### 9.2 Debug Mode

- `LOG_LEVEL=DEBUG ./scripts/start.sh` turns on verbose logs for every process.
- Run one process alone for stepping through code, for example `uvicorn web.api.main:app --host 127.0.0.1 --port 3000 --reload`.
- Run `python scripts/health_check.py` to see which process is not responding.

### 9.3 Logs

- Every process writes JSON logs to standard output with `process` and `case_id` fields.
- To follow one case across processes, search all process output for its `case_id`.
- The audit log is in the `audit_log` table. Each row shows the agent, the action, the rules used (`rule_ids`) and the data used (`data_refs`):
  `psql "$DATABASE_URL" -c "select * from audit_log where case_id = '<id>' order by id"`.
- Logs never contain credentials or restricted values. If you see one, treat it as a defect.
