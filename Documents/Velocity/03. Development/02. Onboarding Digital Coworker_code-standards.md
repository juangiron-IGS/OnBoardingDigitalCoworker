## 1. Introduction

### 1.1 Purpose
This document sets the coding standards and best practices for Onboarding Digital Coworker, so the six-person team writes consistent, maintainable and secure code. This matters most because the work is split into parallel lanes and has to reach the October 28, 2026 submission.

### 1.2 Scope
These standards apply to all code written for:
- Production code (web app, API, case service, orchestrator and agents, MCP servers)
- Test code
- Scripts and automation (start, health-check and reset commands, database migrations, seed scenarios)
- Configuration files and data files (rules catalog in YAML/JSON/CSV, `.env.example`, CI workflow)

### 1.3 Principles
- **Readability**: Code should be easy to read and understand
- **Consistency**: Follow established patterns, and let tools enforce them where possible
- **Simplicity**: Prefer simple solutions
- **Maintainability**: Write code that is easy to modify
- **Security**: Security is not optional. The approval gate and the "no write to JobDiva" rule (BR-002, BR-014) are never bypassed for convenience

### 1.4 Development Priorities
These standards support two project-level decisions recorded in Phase 3's Answers record:

- **MVP first (`extra.mvp-priority`).** The Must scope (J1 and J2, their Must agents, the approval gate, the audit log, the JobDiva connectors and mocks, and the negative governance tests) is built and reviewed before any Should or Could item. Code for Should and Could agents is not merged ahead of a working MVP.
- **Parallel lanes (`extra.parallel-lanes`).** Lane A (governance core) and Lane B (intelligence and connectors) meet only at the case service API and the MCP tool signatures. Those interface contracts are defined first and stubbed in `code/contracts/`. Changing one needs a pull request approved by someone from each lane (Tech Doc §6.4), and the PR template marks it (Section 8.3).

## 2. General Guidelines

### 2.1 Code Organization

> **Source:** Phase 3's Answers record, `struct.list` (STRUCT-001 to STRUCT-009) for the folder-to-component mapping, `repo.list`† for the single-monorepo strategy, and `ctx.list` (CTX-002) for the team size. The mapping is not restated here. The layering pattern inside each component is resolved in Tech Doc §5.1, because `struct.list` deferred it to Technical Documentation. This document does not propose a different one.

The repository is a single monorepo (`repo.list`†): the existing `Movers-OnBoarding` repository, with all source under `code/` and one folder per component group inside it (Tech Doc §5.1). Code in one lane's folders must not import from the other lane's internals. It uses the agreed interface (case service API or MCP tool signatures) instead.

The team has six members. Limits are therefore review-enforced, backed by the automated linter and formatter gates in Section 4, and not by heavier tooling.

#### File Length
| Metric | Target | Maximum |
|--------|--------|---------|
| Lines per file | 300 | 500 |
| Functions per file | 15 | 25 |
| Lines per function | 25 | 50 |

> These limits are calibrated for a team of six and are not recorded in the Answers records. A reviewer may accept an exceeding file or function with a stated reason (for example a generated migration or a long rule table).

### 2.2 Naming Conventions

> **Source:** Phase 3's Answers record, `conv.list`. CONV-001 to CONV-007 are assumed defaults (†, "establish new conventions" for a greenfield project). Rows are reproduced as recorded.

| Element | Convention | Source |
|---------|------------|--------|
| Python files and modules | `snake_case` | CONV-002† |
| Front-end files | `kebab-case` | CONV-006† |
| Classes / types | `PascalCase` | CONV-003† |
| Functions | `snake_case` | CONV-002† |
| Variables | `snake_case` | CONV-002† |
| Constants | `UPPER_SNAKE_CASE` | CONV-004† |

| Branch names | `feature/<short-description>`, plus the prefixes in Section 8.2 | CONV-007† |

Three points are not covered by `conv.list` and are added here, consistent with it:
- **Database identifiers** (tables, columns, roles) use `snake_case`, because PostgreSQL folds unquoted identifiers to lower case. Quoting mixed-case names is avoided. (Source: PostgreSQL documentation, "Identifiers and Key Words", https://www.postgresql.org/docs/current/sql-syntax-lexical.html)
- **Rules catalog identifiers** follow the rule IDs already used by the catalog, in the checkpoint's `R-<domain>-<number>` form (for example `R-PA-02` for a paperwork rule). The catalog format does not change them.
- **Line endings.** Shell scripts use LF line endings, or they fail in Git Bash and WSL on Windows. The repository root carries a `.gitattributes` with `*.sh text eol=lf`.

Naming is enforced automatically by ruff's `N` (pep8-naming) rules in Section 4.2.

### 2.3 Comments and Documentation

#### When to Comment
- Complex business logic, citing the rule ID or BR/NFR ID it implements
- Non-obvious decisions
- Workarounds, with a TODO that names the follow-up
- Public APIs and MCP tool signatures (docstrings stating inputs, outputs and the errors raised)

#### What NOT to Comment
- Obvious code (self-documenting)
- Code that should be refactored instead
- Version history (use git)

No live lookup tool (`context7` or web search) was available when this document was generated. The references were not re-fetched, and no version was pinned because the Python and framework versions are not fixed in the source documents. They should be re-checked when versions are confirmed.
>
> Folder paths below come from `struct.list`. The layering pattern inside each folder is defined in Tech Doc §5.1 and §6.1 and is not repeated here.

### 3.1 Python (web/API layer, case service, agents glue code, MCP servers)

**Idiom 1: Type hints on public functions and explicit `None` handling** (CONV-005†). (Source: PEP 484, https://peps.python.org/pep-0484/, and PEP 604, https://peps.python.org/pep-0604/)

```python
# Recommended: typed signature, absence is explicit
def find_rule(rule_id: str) -> Rule | None:
    return _RULES.get(rule_id)

rule = find_rule("R-PA-02")
if rule is None:
    raise RuleNotFound(rule_id="R-PA-02")

# Discouraged: untyped, and returns a sentinel that callers forget to check
def find_rule(rule_id):
    return _RULES.get(rule_id, "")
```

`X | None` requires Python 3.10 or later. Tech Doc §4.1 uses Python 3.12 as the working default, so `X | None` is the standard form.

**Idiom 2: Declare a FastAPI endpoint `async def` only when it awaits non-blocking calls.** A blocking call inside `async def` stalls the event loop for every other request. (Source: FastAPI documentation, "Concurrency and async / await", https://fastapi.tiangolo.com/async/)

```python
# Recommended: blocking database call in a plain def, so FastAPI runs it in a thread pool
@router.get("/cases/{case_id}")
def get_case(case_id: str) -> CaseView:
    return case_service.get_case(case_id)      # synchronous driver call

# Discouraged: blocking call inside async def
@router.get("/cases/{case_id}")
async def get_case(case_id: str) -> CaseView:
    return case_service.get_case(case_id)      # blocks the event loop
```

**Idiom 3: Validate input at the boundary with typed models.** Validated models are the only accepted input to the case service. (Source: Pydantic documentation, https://docs.pydantic.dev/, and FastAPI documentation, "Request Body", https://fastapi.tiangolo.com/tutorial/body/)

```python
from pydantic import BaseModel, Field

# Recommended: the case ID comes from the path (POST /approvals/{case_id}), the body is validated
class ApprovalDecision(BaseModel):
    package_version: int = Field(ge=1)
    decision: Literal["approve", "return", "reject"]
    comment: str | None = Field(default=None, max_length=1000)

# Discouraged: untyped dict passed through to the approval gate
def receive_decision(payload: dict): ...
```

**Agent code.** Velocity 2.0 SDK conventions (agent definition, tool registration, model calls) belong to the Velocity 2.0 documentation and the confirmed spike results in Tech Doc. This document adds no SDK-specific rules. Python code that surrounds the SDK follows the rules above. Prompts, tool arguments and logs must never contain restricted values (SEC-004†), and model calls remain metered and capped per run (TC-004).

**No legal or employment decisions.** No agent code or prompt may decide FLSA status, worker classification, compensation or any other legal employment question. These values come from the source field or from HR. The Coworker only maps them to paperwork, and it escalates any conflict to the Onboarding Team as an exception line. A reviewer rejects code that infers or overrides one of these values.

### 3.2 Agent prompts and skills (`code/agents/<agent>/prompt.md`, `skills/`)

Prompts and skills are submission deliverables, so they follow the same review as code.

- Each agent keeps its prompt in `prompt.md` and its skills in `skills/`, inside the agent's folder. They are versioned in git and never edited only in the Velocity 2.0 console.
- A prompt states the agent's role, the tools it may call and what it must escalate. Only the JobDiva and Workflow agent's prompt mentions write tools.
- Email text, chat text and rule values enter a prompt only inside clearly delimited data sections, never as instructions (Section 5.2).
- Examples in prompts and skills use synthetic data only (SEC-002†). They never contain restricted values (SEC-004†) or credentials (SEC-003†).
- Every rule an agent applies is cited by its rule ID in the output, so the package line and the audit entry can carry it (Section 3.5).

### 3.3 Browser front-end (five views)

> `stack.list` records a lightweight browser front-end (STACK-003) and no specific front-end framework. No framework is assumed here. If one is chosen, add its idioms to this section.

- File names use `kebab-case` (CONV-006†).
- Render any text that came from a user, an agent or a tool with `textContent` (or the framework's escaping equivalent), never `innerHTML`. See Section 5.3. (Source: OWASP Cross Site Scripting Prevention Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)
- No inline event handlers or inline `<script>` blocks. Use ES modules.
- The browser only talks to the API on localhost. It never calls MCP servers, the database or JobDiva directly.
- Role-dependent display (visa, sponsorship, FLSA) uses the policy decision returned by the case service. The front-end never decides authorization itself.

### 3.4 PostgreSQL and SQL (`code/db/`)

- Every schema change, including every table, is a numbered migration in `db/migrations/`. A schema is never edited by hand in a running container.
- Roles and grants live only in `db/roles/`, and role scripts are idempotent. Synthetic seed scenarios live in `db/seed/` (SEC-002†). `scripts/apply_db.sh` applies the three folders in that order (Tech Doc §4.5).
- Application code accesses the database only through parameterized queries (Section 5.2). The driver is psycopg 3, declared in `pyproject.toml`.
- The audit table is append-only (SEC-005†). The `audit_writer` role has `INSERT` and nothing else on it. The `coworker_app` role has `SELECT` only, for the status view. No role has `UPDATE`, `DELETE` or `TRUNCATE` on it. (Source: PostgreSQL documentation, "GRANT", https://www.postgresql.org/docs/current/sql-grant.html)
- **Every audit entry is complete.** It records the case, the agent (or human role), the action, the outcome (completed, refused or failed), the rules used (`rule_ids`) and the data used (`data_refs`, by field name and source, never restricted values). This is the checkpoint's audit log entity and AC9. An `audit.append` call without `rule_ids` must state in a comment why no rule applies.

### 3.5 Rules catalog and templates (`code/rules/`)

- Rules are data, in YAML, JSON or CSV. Changing a rule never requires changing an agent.
- Every rule carries a rule ID and an owner (Onboarding, IT or LDC), and every recommendation and package line cites it.
- Every package line carries a label: `source`, `inferred`, `recommended` or `exception`, plus its source or rule ID. A line without both is invalid and is rejected by the case service.
- YAML is read with `yaml.safe_load`, never `yaml.load` on a general loader. (Source: PyYAML documentation, https://pyyaml.org/wiki/PyYAMLDocumentation)

### 4.2 Linting Rules

> **Source:** Phase 3's Answers record, `tool.list`† (ruff for linting and formatting) and `qual.list` (QUAL-008†). Configuration choices below that go beyond what the records name are drawn from the ruff documentation (https://docs.astral.sh/ruff/).

Configure ruff once, in `code/pyproject.toml`:

```toml
[tool.ruff]
line-length = 88

[tool.ruff.lint]
select = [
    "E", "W",   # pycodestyle errors and warnings (PEP 8)
    "F",        # pyflakes
    "I",        # import sorting
    "N",        # pep8-naming (CONV-002, CONV-003, CONV-004)
    "ANN",      # type annotations (CONV-005)
    "B",        # bugbear: likely bugs
    "UP",       # pyupgrade
    "S",        # bandit-derived security rules
]

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["ANN", "S101"]   # asserts and untyped test functions are normal in tests
```

`target-version` is not set here, because the Python version is not yet fixed. It is inferred from `requires-python` once the spike confirms it.

CI runs `ruff check .` and fails the build on any finding (QUAL-008†). A `# noqa` suppression must name the rule code and carry a one-line reason. A blanket `# noqa` is not accepted in review.

### 4.3 Formatting

The formatter is `ruff format`, configured by the same `[tool.ruff]` section (CONV-001†, `tool.list`†). It is Black-compatible and uses an 88-character line length. PEP 8's 79-character figure is the traditional default. PEP 8 explicitly allows teams to agree a longer limit, and this project uses the formatter's default. (Source: PEP 8, https://peps.python.org/pep-0008/#maximum-line-length, and ruff formatter documentation, https://docs.astral.sh/ruff/formatter/)

CI runs `ruff format --check .` and fails if any file would change. Locally, developers run `ruff format .` before committing.

## 5. Security Standards

> Sections 5.1 to 5.5 are the industry-standard secure coding baseline. They apply regardless of what `sec.list` records, and they are written for the assumed Python/FastAPI/PostgreSQL stack. Section 5.6 lists only what goes beyond the baseline. (Sources: OWASP Cheat Sheet Series, https://cheatsheetseries.owasp.org/, and the technology documentation named in each subsection.)

### 5.1 Input Validation

Validate every input at the boundary: HTTP requests, MCP tool arguments, rules files and any text parsed from an email.

- Use typed Pydantic models with explicit length and range limits (Section 3.1, Idiom 3). Reject unknown or malformed values. Do not repair them silently.
- Allow-list values where the set is known (decisions, action names, role names).
- Validate on the server even if the front-end already checked. Never trust the role selector value without the case service confirming it.
- An invalid input produces an error naming the exact field, never an internal message (Section 9).

(Source: OWASP Input Validation Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

### 5.2 Injection Prevention (SQL, command, etc.)

All database access uses parameterized queries. SQL is never built by string concatenation or f-strings with external values.

```python
# Recommended: placeholders, values sent separately (psycopg 3 style)
cur.execute(
    "SELECT id, package_version FROM cases WHERE id = %s",
    (case_id,),
)

# Discouraged: SQL injection
cur.execute(f"SELECT id, package_version FROM cases WHERE id = '{case_id}'")
```

- Identifiers (table or column names) are never taken from input. If one must vary, choose it from a fixed allow-list in code.
- No `shell=True` in `subprocess` and no `eval` or `exec` on any external text. The start, health-check and reset scripts pass arguments as lists.
- Email text and rule values are data. They are never interpolated into prompts as instructions without being clearly delimited as data.

(Sources: psycopg 3 documentation, "Passing parameters to SQL queries", https://www.psycopg.org/psycopg3/docs/basic/params.html, and OWASP SQL Injection Prevention Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

### 5.3 XSS / Output Encoding Prevention

The views display text that originates from simulated emails, chat messages and agent output, so output encoding is required.

- Render dynamic text with `textContent` or the front-end framework's auto-escaping. Never `innerHTML` with data.
- The API returns JSON with the correct content type, through FastAPI's response models. It does not hand-assemble HTML from data.
- Simulated Teams messages and alerts are displayed as encoded text in the alerts view.

(Source: OWASP Cross Site Scripting Prevention Cheat Sheet, link in Section 3.3)

### 5.4 Secrets Management

- Secrets (JobDiva credentials, database password, Velocity 2.0 settings) live in a local `.env` file that is outside version control. Only `.env.example`, with no real values, is committed (`tool.list`†, SEC-003).
- Read them from the environment at startup. Never hardcode them or put them in source, test fixtures, seed files or CI logs.
- The JobDiva token is held in memory only and confined to the JobDiva READ MCP server. No other process receives it (SAD §3.2).
- `JOBDIVA_MODE` accepts only `mock` (default) or `sandbox`, and is fixed at startup. An unrecognized value stops the process at startup.
- Logs record a field reference, never a secret or a restricted value (Section 9 and SEC-004†).

```python
# Recommended: read once at startup, fail fast, never log the value
JOBDIVA_MODE = os.environ.get("JOBDIVA_MODE", "mock")
if JOBDIVA_MODE not in {"mock", "sandbox"}:
    raise SystemExit("JOBDIVA_MODE must be 'mock' or 'sandbox'")

# Discouraged
JOBDIVA_TOKEN = "eyJhbGciOi..."                 # hardcoded
logger.info("Calling JobDiva with %s", token)   # secret in a log
```

(Sources: OWASP Secrets Management Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html, and ruff `S` rules for hardcoded-secret detection, https://docs.astral.sh/ruff/rules/#flake8-bandit-s)

### 5.5 Security Checklist
- [ ] No hardcoded credentials, and no credentials in the repository or in any log
- [ ] Input validation on all endpoints and MCP tool arguments
- [ ] Parameterized database access only
- [ ] Proper authentication checks (the simulated role comes from the case service)
- [ ] Authorization verified for every operation, and actions only with an approval ID for the current package version
- [ ] Sensitive data protected: restricted data shown only to authorized roles
- [ ] Error messages don't leak internal information

## 6. Testing Standards

> **Source:** Phase 3's Answers record, `qual.list`. All of QUAL-001 to QUAL-008 are assumed defaults (†). They are carried forward as assumptions. Illustrative test examples for each required type are in Tech Doc §7.4 and are not duplicated here.

### 6.1 Required Test Types and Coverage

| Type | Coverage Target | Source |
|------|-----------------|--------|
| End-to-end tests of the Must journeys J1 and J2 on the seed scenarios | Both journeys must pass in CI | QUAL-001† |
| Unit tests of the rule lookups | Counted in the 70% line-coverage target | QUAL-002†, QUAL-006† |
| Connector tests in mock mode | Counted in the 70% line-coverage target | QUAL-003†, QUAL-006† |
| Negative governance tests, one for every inviolable rule listed in QUAL-004 | 100% of them must pass. A failure blocks merge | QUAL-004†, QUAL-008† |

- **Libraries.** pytest with pytest-cov for running tests and measuring coverage (QUAL-005†). `unittest.mock` for test doubles (QUAL-005†).
- **Coverage gate.** 70% line coverage overall, enforced in CI (QUAL-006†).
- **Negative governance tests.** These are required for MVP completion, since they protect BR-002 and BR-014. Priority follows `extra.mvp-priority`: tests for Must behavior come first.
- **Test data.** Synthetic only (SEC-002†).

### 6.2 Test Naming and Structure

- Tests are named `test_<behavior>` (QUAL-007†), and the name states the behavior and not the function, for example `test_approval_rejected_when_package_version_is_stale`.
- Each test follows Arrange-Act-Assert (QUAL-007†).
- Mocks are used only at connector boundaries, such as the MCP servers and Velocity 2.0 model calls, never to replace the case service or approval gate logic under test (QUAL-007†).

> **Considered, not adopted:** pytest's own documentation offers the `monkeypatch` fixture for replacing attributes in tests (https://docs.pytest.org/en/stable/how-to/monkeypatch.html). `qual.list` already fixes `unittest.mock` as the test-double mechanism (QUAL-005†), so `monkeypatch` is not used for test doubles.

## 7. Code Review Standards

### 7.1 Review Checklist

#### Functionality
- [ ] Code works as intended
- [ ] Edge cases handled
- [ ] Error handling appropriate (Section 9)
- [ ] No obvious bugs

#### Code Quality
- [ ] Follows coding standards (this document)
- [ ] No code duplication
- [ ] Functions are focused (SRP)
- [ ] Naming is clear and matches Section 2.2
- [ ] Code stays inside its own lane's folders, or goes through the agreed interface

#### Security
- [ ] Input validation present
- [ ] No security vulnerabilities
- [ ] Authentication/authorization correct
- [ ] Sensitive data protected, and no restricted value or secret reaches a log
- [ ] No path that writes to JobDiva, and no action without an approval ID for the current package version
- [ ] Every audit entry carries the case, agent, action, outcome, rules used and data used (Section 3.4)
- [ ] Every package line carries a label and its source or rule ID (Section 3.5)
- [ ] No agent code or prompt decides FLSA, worker classification or compensation. Conflicts are escalated (Section 3.1)

#### Performance
- [ ] No obvious performance issues
- [ ] Database queries optimized
- [ ] No memory leaks
- [ ] Caching used appropriately (see Section 10.2)

#### Testing
- [ ] Tests included and meaningful, matching Section 6's required types
- [ ] Edge cases tested

## 9. Error Handling

> No `conv.list` or `sec.list` entry requires a specific error-handling approach. The pattern below applies the FastAPI and Python documented idioms to the project's own failure behavior. Source: FastAPI documentation, "Handling Errors", https://fastapi.tiangolo.com/tutorial/handling-errors/, and Python documentation, "Errors and Exceptions", https://docs.python.org/3/tutorial/errors.html. SEC-003† and SEC-004† apply to every message and log line.

**Principles**
- **Fail visibly, keep state.** When a dependency fails, the step fails visibly. The case keeps its state, the package status becomes blocked, an alert is shown and the failure is logged (SAD §2.2).
- **A refusal is a normal outcome and is audited.** A refused approval or a refused action produces an audit entry, never a silent drop.
- **Catch specific exceptions** and never use a bare `except:`. Re-raise with `raise ... from exc` so the cause is kept.
- **Error text for users names the field or the reason**, never a stack trace, a SQL fragment or a secret.
- **Logs carry the shared case ID** (correlation ID) in every process, so a failure can be followed across the web app, case service and MCP servers. Restricted values are logged by field reference, for example `field=visa_status`, never by value.

Governance refusals share one base class in `services/case_service/domain/errors.py` (Tech Doc §6.1). The router for the affected feature catches the refusal and returns HTTP 409 with the reason and the current package version. No global exception handler is used for this.

```python
# services/case_service/domain/errors.py
class GovernanceError(Exception):
    """Base class for refusals that are expected, audited outcomes."""

    def __init__(self, reason: str) -> None:
        super().__init__(reason)
        self.reason = reason


class ApprovalRefused(GovernanceError):
    """reason: "no_approval" | "version_mismatch" (BR-002)."""


# web/api/routers/approvals.py (excerpt, see Tech Doc §6.1)
try:
    approval_id = svc.record_approval(case_id, decision.package_version, role)
except ApprovalRefused as refusal:
    # The case service has already written the audit entry for the refusal
    raise HTTPException(
        status_code=409,
        detail={"refused": refusal.reason, "current_version": svc.current_package_version(case_id)},
    ) from refusal


# Recommended: specific exception, cause preserved, case ID in the log, no restricted value
try:
    result = jobdiva_read.search_duplicate(person_ref, start_date)
except JobDivaUnavailable as exc:
    logger.error("duplicate search failed", extra={"case_id": case_id})
    raise StepFailed(case_id=case_id, step="duplicate_search") from exc

# Discouraged: swallows everything and leaks a value
try:
    result = jobdiva_read.search_duplicate(person_ref, start_date)
except Exception as exc:
    print(f"failed for {candidate_visa_status}: {exc}")
```

## 10. Performance Guidelines

> The project runs on localhost with synthetic data and a small data volume (TC-002, TC-003). These guidelines prevent avoidable problems and do not call for scale-oriented engineering. Each engine- or framework-specific point names its source.

### 10.1 Database
- Index columns used in lookups and joins, such as case ID, package version and approval ID. The audit table is read by case ID. (Source: PostgreSQL documentation, "Indexes", https://www.postgresql.org/docs/current/indexes.html)
- Avoid N+1 queries. Fetch a case with its package lines in one query or a join, not one query per line.
- Paginate any list that can grow, such as the alerts view and the audit view.
- Reuse database connections through a pool and do not open one per request. (Source: psycopg 3 documentation, "Connection pools", https://www.psycopg.org/psycopg3/docs/advanced/pool.html)

### 10.2 Caching
- The rules catalog is loaded by the case service at startup and on update, so it is not re-read from disk per lookup.
- Do not cache approval state, package versions or approval decisions. They must always read current database truth, because the approval gate depends on it.
- Any cache needs an explicit invalidation rule and a stated TTL, and a reviewer should challenge a cache that sits in front of a governance check.

### 10.3 API
- Keep payloads small and return only the fields a view needs.
- Paginate list endpoints. (Source: FastAPI documentation, "Query Parameters", https://fastapi.tiangolo.com/tutorial/query-params/)
- Compression (FastAPI `GZipMiddleware`, https://fastapi.tiangolo.com/advanced/middleware/) and rate limiting are not needed for a loopback-only demo. Add them if a hosted environment replaces localhost.

### 10.4 Model Usage
- Model usage must stay within the assigned budget (TC-004). Use smaller models for extraction work where quality allows, respect the per-run usage cap, and log usage per run and per case.
- Avoid repeated model calls for the same input within one run. Reuse the earlier result.
