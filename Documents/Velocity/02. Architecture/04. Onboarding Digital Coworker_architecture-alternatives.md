## 1. Architecture Alternatives

### Alternative A: Modular Monolith with In-Process Tool Adapters (single local service, SQLite)

#### A.1 Concept
One local service hosts the web/API layer, the Onboarding Orchestrator and specialized agents (running on the Velocity 2.0 runtime), the approval gate, the rules catalog loader and the audit log. Every enterprise mock is an in-process tool adapter behind one connector interface, and all case data lives in a single embedded SQLite file. It favors demo-day availability (NFR-AVAIL-001, 9%), immediate consistency of approval and version checks (NFR-REL-006, 35% of Reliability) and trivial reset and reproducibility. It complies with TC-001 to TC-005: Velocity 2.0 runs agents and models, everything runs on localhost, adapters serve synthetic data only and expose no JobDiva write path, and model calls are metered centrally. It deviates from no STACK item. STACK-004 allows "tool or MCP server", and STACK-006 leaves the database open, so SQLite is a choice rather than a substitution.

#### A.2 Architecture Diagram
```text
 Browser (5 views, simulated role selector)
              |
              v
+---------------------------------------------------------------+
| Local service (single process, localhost)                      |
|                                                                |
|  Web / API layer                                               |
|        |                                                       |
|  Onboarding Orchestrator (Velocity 2.0 runtime)                |
|    |-- Intake & Validation agent                               |
|    |-- Policy & Case Setup agent                               |
|    |-- JobDiva & Workflow agent (only simulated-action writer) |
|    `-- Access & Equipment / Follow-up / Knowledge agents       |
|        |                                                       |
|  Approval gate | Rules catalog (YAML/JSON) | Audit log         |
|        |                                                       |
|  In-process tool adapters (mock JobDiva, Outlook, Teams,       |
|  Chelsea Tech, Paychex, LDC tracker, knowledge base)           |
|        |                                                       |
|  SQLite file: cases, package versions, approvals, audit        |
+---------------------------------------------------------------+
              |
              v  model calls via Velocity 2.0 (metered, logged)
```

#### A.3 Component Breakdown

| Component | Purpose | Technology |
|-----------|---------|------------|
| Web app (5 views) | Chat, simulated inbox, approval, alerts, status, with role selector | Lightweight browser front-end served by the local service (browser on desktop) |
| API / web layer | Serves views, receives approval decisions | Python, FastAPI (assumed default, STACK-006) |
| Onboarding Orchestrator and agents | Case routing, intake, validation, package assembly, simulated actions | Velocity 2.0 runtime (STACK-001, STACK-002) |
| Approval gate | Checks that the approval ID matches the current package version before any action | In-process module, one DB transaction |
| Tool adapters (mocks) | Simulated JobDiva, Outlook, Teams, Chelsea Tech, Paychex, LDC tracker, knowledge base | In-process tool functions behind one connector interface (STACK-004) |
| Rules catalog and templates | Paperwork, kit, owner and notification rules as data | YAML/JSON/CSV files (STACK-005) |
| Case store and audit log | Cases, package versions, approvals, append-only audit | SQLite (WAL mode) |

#### A.4 Deployment Model
A single process on the team member's or reviewer's machine, started with one command from the repository, with all settings in `.env` (`JOBDIVA_MODE=mock` by default). There is one environment (localhost). A reset command deletes the SQLite file and reloads the seed scenarios. A backup demo video covers failure on the day.

#### A.5 Strengths
- The highest demo-session availability (NFR-AVAIL-001, NFR-AVAIL-002): one process, one file, nothing to orchestrate on stage.
- Approval, version and duplicate checks run in one local transaction (NFR-REL-006, NFR-REL-002).
- Single correlated log and database per case ID give the best analysability (NFR-MAINT-003).
- Fastest view response, since reads are local (NFR-PERF-002).
- One install step with no container runtime (NFR-COMPAT-003).

#### A.6 Weaknesses
- The write boundary (only the JobDiva and Workflow agent, never JobDiva itself) is enforced by code convention inside one address space (NFR-SEC-003, NFR-SEC-007).
- Secrets and restricted data share a process and log stream with every module, so redaction relies on discipline (NFR-SEC-005, NFR-SEC-002).
- SQLite offers no database roles, so audit immutability rests on triggers and application behavior (NFR-SEC-004).
- Modules are coupled to the host app, which weakens reuse and the pilot swap from mock to real connectors (NFR-MAINT-001, NFR-MAINT-002, NFR-COMPAT-002).
- A single failure domain and a single-writer database limit concurrency and growth (NFR-PERF-003).

### Alternative B: Hub-and-Spoke Orchestrator with One MCP Server per Enterprise System (PostgreSQL)

#### B.1 Concept
The Onboarding Orchestrator and agents run on Velocity 2.0 and use a local case service that owns the case store, approval gate and audit log in PostgreSQL. Each enterprise system (JobDiva, Outlook, Teams, Chelsea Tech, Paychex, LDC tracker, knowledge base) is its own MCP server process. Write tools are registered only in the JobDiva and Workflow server, which re-verifies the approval ID and package version itself. Read-only JobDiva access lives in a separate server that holds the token. This gives process-level enforcement of the highest-weighted security scenarios (NFR-SEC-003, 41% of Security; NFR-SEC-007) and keeps each connector independently replaceable (STACK-004, NFR-COMPAT-002). It complies with TC-001 to TC-005: Velocity 2.0 hosts runtime and models, all processes bind to localhost, only synthetic data flows, no server exposes a JobDiva write tool in the baseline, and model usage is metered in the orchestrator. It adds PostgreSQL and a container runtime; this is not a deviation from any STACK item because STACK-006 leaves the database open.

#### B.2 Architecture Diagram
```text
 Browser (5 views, simulated role selector)
              |
              v
+---------------------------+        +-----------------------------+
| Web app + API (localhost) |<------>| Case service                |
+---------------------------+        |  approval gate, rules       |
                                     |  catalog, audit writer      |
                                     |        |                    |
                                     |   PostgreSQL (cases,        |
                                     |   versions, approvals,      |
                                     |   append-only audit)        |
                                     +--------------+--------------+
                                                    ^
                                                    |
                          Velocity 2.0: Onboarding Orchestrator + agents
                                                    |
        +----------+----------+----------+----------+----------+---------+
        |          |          |          |          |          |         |
   JobDiva     JobDiva &   Outlook    Chelsea    Paychex     LDC     Knowledge
   READ MCP    Workflow    mailbox    Tech MCP   MCP         tracker  base MCP
  (token held  MCP (only   MCP                               MCP
  here, read-  write tools,
  only)        checks
               approval ID)
```

#### B.3 Component Breakdown

| Component | Purpose | Technology |
|-----------|---------|------------|
| Web app (5 views) | Chat, simulated inbox, approval, alerts, status, role selector | Lightweight browser front-end (STACK-003) |
| API / web layer | Serves views, receives decisions, calls the case service | Python, FastAPI (assumed default, STACK-006) |
| Case service | Case state, package versions, approval gate, audit writer, rules loader | Python, FastAPI, PostgreSQL |
| Onboarding Orchestrator and agents | Routing, intake, validation, package assembly | Velocity 2.0 runtime (STACK-001, STACK-002) |
| JobDiva READ MCP server | Reads start, start notes and duplicate search from the mock, or from the sandbox when credentials exist | Python MCP server; token in memory only, loaded from `.env` |
| JobDiva and Workflow MCP server | The only server with write tools (simulated actions); re-verifies approval ID and package version | Python MCP server |
| Other mock MCP servers | Outlook, Teams, Chelsea Tech, Paychex, LDC tracker, knowledge base | Python MCP servers behind one interface (STACK-004) |
| Rules catalog and templates | Paperwork, kit, owner and notification rules as data | YAML/JSON/CSV files (STACK-005) |
| Case store and audit log | Durable state; audit table writable by INSERT only | PostgreSQL in a local container |

#### B.4 Deployment Model
All components run on localhost, each as its own process, started by one script or Compose file from the repository. PostgreSQL runs in a local container with a named volume. There is one environment. `.env.example` ships with `JOBDIVA_MODE=mock`, and the mode is fixed at startup and never switches at runtime. The mock stores of the simulated systems live in the same PostgreSQL instance, so a simulated action and its audit entry can commit together. A reset command recreates the volume and reloads the seed scenarios, and a backup demo video covers failure on the day.

#### B.5 Strengths
- The write boundary is enforced by process and tool registration, not by convention (NFR-SEC-003, NFR-SEC-007).
- The JobDiva token and other secrets are confined to the connector processes that need them (NFR-SEC-005).
- Audit immutability can be enforced with a database role that has INSERT-only privilege (NFR-SEC-004).
- Each mock is physically separate and replaceable by the real system without touching agents (NFR-COMPAT-002, NFR-MAINT-001, NFR-MAINT-002, NFR-COMP-001).
- Failure of a Should connector is isolated, so J1 and J2 continue (NFR-REL-004).

#### B.6 Weaknesses
- Roughly nine processes plus a container make the demo more fragile than a single process (NFR-AVAIL-001).
- Simulated actions and audit entries span processes. Atomicity depends on shared-database commits and idempotency keys (NFR-REL-002).
- Setup needs a container runtime, which lowers portability and reproducibility (NFR-COMPAT-003).
- Logs from several processes need correlation IDs to stay analysable (NFR-MAINT-003).
- It needs MCP and container skills that the record does not confirm the team has (Section 0.3, point 3).

#### B.7 Cost Estimate

| Compute | $0/month | Local machines; about nine lightweight processes plus one database container |
| Storage | $0/month | Local PostgreSQL volume, well under 1 GB of synthetic data |
| Networking | $0/month | Localhost only |
| Licensing / Services | $40–$264/month | Model usage $40–$120 (TC-004). Plus $0–$144 only if the container runtime needs a paid per-seat tier (six seats at up to $24); a free runtime avoids this. Velocity 2.0 license excluded |
| **Total (est.)** | **$40–$264/month** | Assumed planning range; no numeric budget is stated in the record |

### Alternative C: Event-Driven Agent Pipeline over a Durable Event Log (PostgreSQL + NATS JetStream)

#### C.1 Concept
Case changes are published as events on a durable local stream. The specialized agents and connector workers are asynchronous consumers that react to events, with state kept in PostgreSQL via a transactional outbox. Parallel fan-out lets agents overlap model calls, and at-least-once delivery with idempotent consumers makes retries of approved actions natural (NFR-REL-005, NFR-PERF-003). It complies with TC-001 to TC-005: Velocity 2.0 runs the agents and models, everything binds to localhost, workers use synthetic mocks with no JobDiva write path, and the orchestrator meters model usage. **Deviation from the Stack Context:** it introduces NATS JetStream, a message broker that no STACK item establishes. The pattern needs a durable event log, and STACK-006 does not exclude it. It also adds a second store to keep consistent.

#### C.2 Architecture Diagram
```text
 Browser (5 views)
        |
        v
 Web app + API ---> Case service (PostgreSQL + transactional outbox)
        ^                          |
        |                          v publishes case events
        |             +---------------------------+
        |             |  NATS JetStream           |
        |             |  (durable local stream)   |
        |             +-----+---------+-------+---+
        |                   |         |       |
        |                   v         v       v
        |             Intake &    Policy &   JobDiva & Workflow
        |             Validation  Case Setup worker (only writer;
        |             worker      worker     validates approval)
        |                   |         |       |
        |                   +----+----+-------+
        |                        v
        |             Connector workers (mock JobDiva, Outlook,
        |             Teams, Chelsea Tech, Paychex, LDC, KB)
        |
        `---- status / alerts / audit projections (read models)
```

#### C.3 Component Breakdown

| Component | Purpose | Technology |
|-----------|---------|------------|
| Web app (5 views) | Chat, simulated inbox, approval, alerts, status | Lightweight browser front-end (STACK-003) |
| API / web layer | Serves views from read projections, accepts commands | Python, FastAPI (assumed default, STACK-006) |
| Case service and outbox | Case state, package versions, approval records, event publication | Python, PostgreSQL |
| Event stream | Durable, replayable case events and work queues | NATS JetStream (new component; deviation stated in C.1) |
| Agent workers | Intake, validation, policy and package agents as event consumers | Velocity 2.0 runtime (STACK-001, STACK-002) |
| JobDiva and Workflow worker | Sole executor of simulated actions, validating the approval ID and version on each event | Python worker |
| Connector workers | Mock systems behind one interface | Python MCP servers or tool workers (STACK-004) |
| Read projections | Status, alerts and audit views built from events | PostgreSQL views/tables |
| Rules catalog and templates | Rules as data | YAML/JSON/CSV files (STACK-005) |

#### C.4 Deployment Model
All components run on localhost: the broker and PostgreSQL in local containers, the other pieces as local processes started by one script or Compose file. There is one environment, with `JOBDIVA_MODE=mock` fixed at startup. A reset must purge both the stream and the database volume before reloading the seed scenarios.

#### C.5 Strengths
- Parallel fan-out lets agents overlap model calls, helping the 5-minute turnaround (NFR-PERF-001).
- Idempotent consumers make retrying approved actions with the same approval ID a native behavior (NFR-REL-005).
- Workers are independent, so a failed Should agent does not stop the Must journeys (NFR-REL-004).
- Concurrent cases and the growth path to the pilot scale horizontally (NFR-PERF-003).
- The event log is naturally append-only, which supports audit (NFR-SEC-004).

#### C.6 Weaknesses
- Eventual consistency conflicts with the immediate-consistency operations: approval versus current version, duplicate prevention and keeping a rejected case stopped (NFR-REL-006, NFR-USE-003).
- The most moving parts, including a broker, so the lowest demo-day availability and portability (NFR-AVAIL-001, NFR-COMPAT-003).
- Restricted data and the approval gate are spread across many consumers and event payloads (NFR-SEC-002, NFR-COMP-002).
- Redelivery can re-trigger model calls, which makes the model budget harder to bound (NFR-PERF-004).
- Tracing a case across asynchronous consumers is harder (NFR-MAINT-003).

#### C.7 Cost Estimate

| Category | Estimate | Notes |
|----------|----------|-------|
| Compute | $0/month | Local machines; more processes and two containers (broker and database) |
| Storage | $0/month | Local database volume and stream files, well under 1 GB |
| Networking | $0/month | Localhost only |
| Licensing / Services | $50–$150/month | Model usage $50–$150, slightly higher for retries and redelivery (TC-004). NATS is open source ($0). Velocity 2.0 license excluded |
| **Total (est.)** | **$50–$150/month** | Assumed planning range; no numeric budget is stated in the record |

## 6. Recommendation

### Primary Recommendation: Alternative B — Hub-and-Spoke Orchestrator with One MCP Server per Enterprise System (PostgreSQL)

Alternative B wins with a Final Score of 4.218 against 4.052 for A and 3.338 for C. The result is driven by Security, the heaviest attribute at 24%, where B scores 4.79 against 3.19 for A. The largest single scenario in the tree is NFR-SEC-003, the approval gate and action authorization (41% of Security). Under B, write tools exist only in the JobDiva and Workflow server, which re-verifies the approval ID and package version. B is the only alternative that enforces BR-002 and BR-014 by process boundary and not by convention. Its main cost is Availability, scored only 3.12 ("Partial"), because a demo session depends on more moving parts. The lead over A is modest (0.166), and the mitigations in Section 7 are part of the recommendation.

**Why Alternative B wins:**
- **Security (4.79):** Process-level write isolation (NFR-SEC-003, NFR-SEC-007), an INSERT-only audit role (NFR-SEC-004) and a token confined to one server (NFR-SEC-005) each score 5.
- **Reliability (4.26):** Durable PostgreSQL storage scores 5 (NFR-REL-001). Atomicity of action and audit (NFR-REL-002) and consistency of approval, version and duplicates (NFR-REL-006) score 4, a notch below A's single-transaction 5, because of the process boundary.
- **Compliance (4.22):** Physically separate mocks make the simulation boundary explicit (NFR-COMP-001, 5).
- **Compatibility (4.18) and Maintainability (4.33):** One MCP interface across mock, sandbox and real systems (NFR-COMPAT-002, NFR-MAINT-001, NFR-MAINT-002, each 5) supports the pilot swap and the reuse criterion.
- **Usability (4.00) and Performance (4.00):** Both are solid, not leading. Model latency dominates the 5-minute turnaround (NFR-PERF-001) in every alternative.

**Why not Alternative A (Modular Monolith, 4.052):** A is the runner-up and the better choice on Availability (5.00 against 3.12), Reliability (4.50), Usability (4.34), view responsiveness and setup simplicity. It is the right choice instead of B if the day-one spike shows the team cannot deliver and run multiple MCP servers and a container database before October 28, or if the architect weights demo-day availability above write-boundary isolation. Its weakness is that the approval and JobDiva-read-only boundaries are enforced only by code discipline (NFR-SEC-003, NFR-SEC-007 both score 3). A can also serve as B's fallback: the connector interface is the same, so the in-process adapters can later become MCP servers.

**Why not Alternative C (Event-Driven Pipeline, 3.338):** C is better on retry idempotency (NFR-REL-005) and growth (NFR-PERF-003). But eventual consistency scores 2 on NFR-REL-006, the largest Reliability scenario, because the requirement is that approval, version and duplicate checks are consistent immediately. It also has the lowest availability (2.12) and adds a broker the stack does not establish. It would be reconsidered only if volumes grow well beyond the pilot (see Section 8).

## 8. Future Considerations

1. **Decide on sandbox-write mode for JobDiva**
   The record holds both a read-only decision and a request to create synthetic test records in the sandbox. Allowing writes requires changing BR-014 to "never writes to production JobDiva", committee approval and an API user with sandbox write permission. Under B this is a separate `sandbox-write` mode on the JobDiva and Workflow server, off by default, that refuses to run unless the base URL is the sandbox.
   *Trigger:* Committee decision on BR-014 and receipt of JobDiva sandbox credentials.

2. **Replace mocks with real systems for the pilot**
   Each MCP server can be swapped for the real Outlook mailbox, Chelsea Tech, Paychex or LDC tracker without changing agents. Each swap should go through a read-only run first and a new security review.
   *Trigger:* Business owner agrees to a 4–6 week pilot with one client or contract type.

3. **Add Microsoft Teams as a real channel**
   The Teams mock becomes a real notification and chat channel once a bot can be registered in the INSPYR tenant. The orchestrator and agents stay unchanged, since the user channel is already behind an interface.
   *Trigger:* A Teams bot registration becomes possible in the INSPYR tenant.

4. **Move the rules catalog to a business-maintained store**
   The catalog is kept as open-format data so Onboarding, IT and LDC can own and version it. A managed store with edit rights, versioning and review would replace the files.
   *Trigger:* Tonya Ramirez's team finishes validating the catalog, or catalog changes become frequent.

5. **Reconsider an event-driven pattern for scale-up**
   If the pilot grows to many concurrent cases or all clients, Alternative C's durable stream and horizontal workers become relevant. Doing so requires solving the immediate-consistency checks (approval and version) at the point of execution.
   *Trigger:* Sustained concurrent case volume that exceeds what one case service and PostgreSQL handle comfortably, or the scale-up to all clients.

6. **Set production and pilot infrastructure budgets**
   No ceiling exists beyond model usage within budget. Before the pilot, production and non-production infrastructure budgets should be set separately so a hosted deployment can be sized and priced with live provider pricing.
   *Trigger:* Pilot approval, when a hosted environment replaces localhost.
